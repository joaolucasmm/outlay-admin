*2026-11-15* · split **test** (20 cases, sources: synthetic) · produced by `evals/report.py` from `evals/runs/*/results.jsonl`.

The model only extracts; the policy engine decides compliance, so what matters here is whether each field is right. Field accuracy is the share of the 5 fields (merchant, date, total, currency, category) that match the label, averaged per case over reps; a null answer on an unreadable receipt counts as right, an invented one as a hallucination.

## Notes

- Dataset fix during this round: the two unreadable cases (rcpt-029, rcpt-030) were first only blurred, and every variant read the printed values correctly against a null label. The generator now replaces every character with '?', and those 2 cases were re-run for all variants; nothing else changed.
- v2 regression found on test only: on rcpt-007 (a US receipt with no tax or tip line), v2's country-first rule left Opus unsure of the country, so it returned a null date (3/3 reps) and a null currency (2/3, which also drops the total). v1 got it right 3/3. Dev showed no such case, so the prompt was not tuned on it; it is the first input for a v3.
- Prompt v2 names receipt labels (IVA, Propina, Efectivo/Cambio, SUMME, Dinheiro/Troco) that the generator also prints. They are common real-world labels, but the overlap may favour v2 on synthetic receipts more than on real photos. The date, amount and total rules in v2 came from the architecture's plan, not from dev failures (dev had none).

## Limits

- Synthetic receipts only (drawn by `evals/generate_receipts.py`). Real anonymized photos are still to be added, so absolute numbers likely overstate accuracy on real photos; the comparison between variants is the useful signal.
